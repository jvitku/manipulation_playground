The question

What is a force token worth when the camera cannot see the quantity that decides success — and where must it enter the model? Lesson 16 left nanoVLA at 45/100 on T1 (CI 35.6–54.8%): it presses competently but cannot feel the hidden click threshold (10 force-aborts) and reads the instruction at chance (45 wrong-button presses). This lesson feeds the 6-D wrench in — through five different doors — and lets the claims board grade ForceVLA's central ablation (Table 3) in miniature: a linear token before the VLM, an MoE before the VLM (the paper's 0% row), a plain concat after it, and the paper's answer, the FVLMoE — a ported LIMoE block whose output is added to the action expert's features right before the head. Two more claims ask the question every force-VLA paper must answer: is the force actually used (the zeroed twin), and does the model notice when the sensor lies (FACT's force-to-noise)? Round 1 measured all of it and landed red — every arm in one clump around the ~50% button lottery — and its diagnosis named the two causes round 2 then attacked with two standard, teachable levers: classifier-free guidance on the instruction (train with the instruction sometimes blanked, sample with the conditional-minus-unconditional difference amplified) and reactive re-planning (execute 2 steps per chunk instead of 8, so the wrench each decision reads is 0.2 s stale, not 0.8 s). Both rounds are on this page, and the board was re-graded after each.

The task

T1 press-until-click, unchanged from lessons 15/16: two buttons, sides swapped per episode, "press the red/blue button", a per-button click threshold \(\sim U(3, 9)\) N that never touches the pixels, and success demands peak |F| < 1.5× threshold — pressing blindly harder loses. All arms train on the same re-recorded T1 demos (200 episodes, position-mode press, run 261101-002511-7bc4) and evaluate on the same held-out seeds, so every gap below is paired. The bar to beat is lesson 16's 45/100, and its failure split frames what a force input can and cannot buy:

lesson-16 failurecountcan a force input fix it?
wrong_button — confident press on the wrong cap45no — which button is in the words, and lesson 16 measured the instruction at chance (c6). The wrench says nothing about colour
force_abort — dug in past 25 N beside or on the cap10yes — the staircase of Fz is exactly what the camera cannot see and the wrench streams at every step

The arithmetic this implies is the honest pre-registration of this lesson: if force fixes when to stop but the words stay at chance, the ceiling sits near the ~50% the button lottery allows plus the pressing gains — well short of the plan's fvlmoe ≥ 80% gate (M2), unless completed presses make wrong_button the dominant, fixable outcome and an instruction gradient finally materialises. The gate bar is fixed either way; a red row is a result, not an embarrassment.

The method

The force token φF. The env's compensated, filtered wrench (sign convention: pressing on a surface reads negative Fz) enters as one linear token: force_in_proj = Linear(6 → 256), the reference's own name and shape (in pi0_force.py it is Linear(6 → 2048) applied to state[7:13] — the 13-D state carries the wrench in its tail, and the state token itself sees it zeroed). EF = φF(wrench) is a [B, 1, 256] token at the trunk width.

The FVLMoE, ported not re-derived. src/nfv/model/limoe_port.py is a PyTorch port of the released LIMoEBlock (ft-robotic/ForceVLA at 79de88f, Apache-2.0, reference names kept; parity against the real JAX block is pinned by fixture to max |Δ| < 1e-5). The block is three stages:

1. Encoder block — one pre-norm ViT layer over the fused sequence: LayerNorm → 8-head self-attention → dropout 0.1 → residual → LayerNorm → MLP (GELU, tanh approximation — the flax default) → residual. This is where the force token first reads the scene.

2. Top-1 tokens-choose router with capacity — flaxformer's TokensChooseScatterRouter, kept mechanic by mechanic. Each token gets expert probabilities and its arg-max expert:

$$p_i = \mathrm{softmax}(W_r\, \tilde{x}_i) \in \mathbb{R}^{E}, \qquad e_i = \arg\max_m p_{i,m}, \qquad g_i = p_{i, e_i},$$

where \(\tilde{x}_i\) is the token times multiplicative jitter noise \(\mathcal U(0.99, 1.01)\) — train only, and only the router sees it; the experts read the raw token. Tokens are flattened over (batch, sequence) and split into groups of ≤ 16 (the reference's _num_groups rule); each expert's buffer per group holds

$$C = \max\big(\mathrm{round}(1.0 \cdot g / E),\; 4\big)$$

slots (capacity factor 1.0, floor 4 — at g = 16 and E = 4 experts that is 4 slots). Buffers fill in order of router confidence (batch-prioritized: tokens sorted by \(g_i\)), and a token that overflows its expert's buffer gets zero expert output — silently. The port logs the fraction left behind precisely because this failure is invisible otherwise. The experts are flaxformer MLPs (wi → ReLU → wo, 256 → 512 → 256 here); then residual and an output projection: \(y = W_o(x + g_i\,\mathrm{Expert}_{e_i}(x_i)\,[\text{slot}_i < C])\).

3. The injection: last-H ADD. The block runs over [E ; EF] — the trunk's output plus the force token, force LAST — and its last H positions are added to the action expert's chunk features right before the velocity head:

$$v = W_{\mathrm{head}}\big(\,f + m\,\big), \qquad m = \mathrm{LIMoE}([E\,;\,E_F])_{[:, -H:]},$$

the reference's action_out_proj(limoe_out[:, -H:] + suffix_out[:, -H:]). A parallel branch summed at the end — not conditioning, not an input token. Note the kept quirk: the last H positions of [E ; EF] are text/pad tokens plus the force token, aligned to the H action steps by position only; it works anyway, and that it works is part of the lesson.

Reference-code facts the paper omits (reading a codebase against its paper): the router's load-balancing and z-losses are computed and never added to any training loss — the capacity cap is the only balancing (the course exposes balance_loss as a switch, coefficient 0.01, Switch Transformer's value); the released sample_actions concatenates a None prefix into the LIMoE call while the cached prefix_out_fix sits computed and unused — the inference path needs a one-line fix before it runs, so the paper's numbers come from compute_loss-consistent training while inference as shipped is broken; the port gives act() and loss() one shared definition. The reference rounds router logits and expert inputs to bf16 (a TPU choice); this course is fp32 end-to-end and the parity fixture pins those dtypes — a documented deviation, not a silent one.

Where each ablation route enters — the five arms of the claims suite, each one door in the schematic below:

none is lesson 16's nanoVLA bit-identically (the ForceInput module holds no parameters and every hook is the identity) — retrained here so the baseline shares the suite's seeds and schedule. prefix_linear appends the one φF token to the trunk input [image ; text ; force]: force enters the "VLM" as a 257th word and self-attention may bind it to anything — Table 3 measured 55%, a 10-point gain over none. prefix_moe runs the whole LIMoE block over that same prefix before the trunk — Table 3's 0% row and the course's built-in expected collapse: the capacity cap zeroes scene tokens before the trunk ever reads them, and the router decides with no instruction context. concat_after broadcasts EF feature-wise onto every trunk output token and fuses with one Linear(2d → d), no MoE — Table 3's "w/o MoE" row, 60%: late fusion already helps; the MoE is the rest. fvlmoe is the full mechanism above — 80% in the paper, the M2 gate here. A sixth route, prompt_bins (ForceBench's numeric prompt: each wrench axis clamped to ±25 N / ±2.5 Nm and quantised to 32 bins, six embedding-table tokens appended to the text), is on the single-preset form as the cheapest reference point; it is not a Table-3 row, so the suite does not train it.

The twin and the noise rows cost no retrain. ``force_noise`` corrupts the wrench where act() reads it (same place the loss does): zero = the force-blind twin, gaussian = FACT's force-to-noise (\(\mathcal N(0, 1\,\mathrm{N})\) per component), shuffle = permute the batch — which at act time has batch size 1 and is therefore a no-op by construction (exercise 3 measures exactly that trap). The suite evaluation rolls the one fvlmoe checkpoint three times (off / zero / gaussian) on the same seeds.

Round 2's levers — instruction dropout + classifier-free guidance, and the re-plan cadence. Round 1 diagnosed two mechanisms (measured below), and each has a standard counter. First, the instruction: training now blanks it per sample with probability p (text_dropout, ModelConfig) — the blank is the model's own constant <unk> text (nfv.model.text.BLANK_INSTRUCTION, the same text lesson 16's arm C rolls on) — so ONE network learns both the conditional velocity field \(v_\theta(x_\tau, \tau \mid \ell)\) and the unconditional \(v_\theta(x_\tau, \tau \mid \varnothing)\). At act time every Euler step combines them with the guidance weight w (cfg_w, an eval knob — no retrain):

$$v_w(x_\tau, \tau) \;=\; v_\theta(x_\tau, \tau \mid \varnothing) \;+\; w\,\big[\,v_\theta(x_\tau, \tau \mid \ell) - v_\theta(x_\tau, \tau \mid \varnothing)\,\big],$$

Ho & Salimans' classifier-free guidance on the flow field: w = 1 is exactly the plain conditioned model (the blank branch is skipped — the default act() is bit-identical to round 1), w > 1 extrapolates past the conditioned prediction along the direction the words add. Why this attacks lesson 16's c6 mechanism precisely: the flow interpolant leaks the mode — at most \(\tau\) the noisy chunk \(x_\tau\) already says which button this sample is drifting toward, so during training the conditional target is largely predictable without the text and the words earn almost no gradient. Dropout denies that free ride half-heartedly (the blank samples force the network to also model the ambiguous field), and CFG then amplifies at sampling time whatever conditional-minus-unconditional difference training did leave: near \(\tau = 1\), before the sample has committed to a mode, \(v_{\mathrm{cond}} - v_{\mathrm{blank}}\) is as close to "what the words say" as this model gets, and w > 1 pushes the sample onto the instructed mode before the leak takes over. Second, the wrench: n_exec_override (eval knob) re-plans after 1–16 executed steps instead of the trained 8 — lesson 4's smoothness-vs-reactivity trade, re-read as sensor staleness: at n_exec 8 the one 10 Hz wrench sample a decision reads is up to 0.8 s old by the time the chunk's last executed step lands, at n_exec 2 at most 0.2 s — short enough that "the staircase is rising" can still gate the press it describes. Both are pure act-time knobs on one checkpoint; both lessons' evaluate forms carry them, and the measured protocol below was fixed before the runs (R1 on the round-1 checkpoint, R2 a 2×2 grid on two dropout-retrained singles with the recipe chosen on the force-blind arm's button match, R3 one suite re-run under that recipe — no tuning on the gated arm).

Motivation — why each choice is in this experiment

Why a port, not a re-derivation. The paper's prose and the released code disagree in two load-bearing places (the injection point reads "to the expert's input" but the code adds to its output; the balance loss is described and never applied). A re-derivation from the paper would silently test a different model. Porting with names kept, pinning parity by fixture against the real JAX block, and documenting every deviation (fp32, aux returned) is the reproducible-research half of this lesson — the force half is the other.

Why the twin and the noise are claims, not extras. This repo has already been burned: at image scale a torque token was simply ignored (TA-SmolVLA 53% vs its zeroed twin 66% — the twin won), and FACT found ForceVLA itself leans on force in only one of five tasks. "Is the force used" therefore ships as two default claims (m2.twin_gap, m2.noise_drop) that every suite eval fills from the one checkpoint — a force lesson that cannot show its input is load-bearing has measured nothing.

Why top-1-with-capacity vs top1 vs soft is a switch. The reference's sparse scatter router and ForceVLA2's dense softmax blend (lesson 18) are different objects that the papers' prose both call "MoE". Keeping ``moe = top1_capacity | top1 | soft`` on one config makes the difference measurable rather than rhetorical, and isolates the capacity cap (the only part that destroys information) from the routing idea itself.

Why the capacity-drop fraction is logged. An overflowing expert buffer zeroes tokens with no error, no NaN, no loss spike — the only symptom is a number nobody computed. The port returns it in aux; training stores the last batch's value per arm in the checkpoint; the eval reports it per decision. At act time it is 0 by construction (batch 1 gives 85 tokens → groups of 1, where the floor of 4 never binds — the reference's own degenerate-grouping rule), which is itself a finding worth a sentence: the cap is a training-time regulariser here.

Theory — MoE routing in 200 words, and the late-fusion rule

Mixture of experts. Replace one MLP with E of them plus a tiny router that assigns tokens to experts. With top-1 routing each token runs through exactly one expert, so parameters grow E-fold while compute per token stays constant — the scaling trick of Switch Transformer. Two classic failure modes drive the machinery: collapse (the router sends everything to one expert; its gradient-rich expert improves, the gap widens) and load imbalance on parallel hardware. Switch adds an auxiliary balance loss; the LIMoE lineage adds per-group capacity: each expert accepts at most C tokens per group of 16, filled in confidence order, overflow dropped to zero. Jitter on the router input decorrelates assignments early in training. ForceVLA inherits all of it via flaxformer — then computes the balance losses and applies none, so capacity alone disciplines the router. At this lesson's scale the MoE is not for throughput: it is a gating hypothesis — that contact and free-space tokens want different processing, which the routing statistics below test directly.

The late-fusion rule. Both ForceVLA (Table 3: MoE before the VLM = 0%) and ForceVLA2 (force into the VLM pathway = 5%) measured the same cliff: force must join after the pretrained vision-language trunk, as a parallel branch or conditioning — never as an input the VLM must survive. nanoVLA's trunk is trained from scratch, so whether the rule transfers to a 2.6 M-parameter "VLM" is a real question, and m2.moe_before_vlm_collapses reports it either way.

The twin and the FACT test: one function, applied where act() and loss() read the wrench
def apply_force_noise(
    wrench: torch.Tensor, mode: str, generator: torch.Generator | None = None
) -> torch.Tensor:
    """The twin / FACT wrench corruptions on a [B, 6] wrench (see the module docstring)."""
    if mode == "off":
        return wrench
    if mode == "zero":
        return torch.zeros_like(wrench)
    if mode == "shuffle":
        perm = torch.randperm(wrench.shape[0], generator=generator, device=wrench.device)
        return wrench[perm]
    if mode == "gaussian":
        noise = torch.empty_like(wrench).normal_(0.0, FORCE_NOISE_SIGMA, generator=generator)
        return wrench + noise
    raise ValueError(f"force_noise={mode!r}")

Why the gate is red — the pre-registered arithmetic, confirmed. (1) The language ceiling held: fvlmoe pressed red 49 / blue 47 across its episodes and scored ~44–46% under both instructions — lesson 16's c6 finding (the flow interpolant leaks the mode, so an eval-time wrong-button cost creates no training-time gradient for reading the words) is untouched by adding force, and it caps every arm near the ~50% button lottery. (2) The hoped-for second gain — force fixing when to stop — did not materialise either: aborts were already rare (6/100 for the blind baseline), one 10 Hz wrench sample per 0.8 s re-plan arrives too late to stop an 8-step open-loop press segment, and behaviour cloning gives no incentive to consult a sensor the demos' velocities barely need (given pixels and depth, the press is almost deterministic — everywhere except the click step itself). (3) More steps is not the lever: 25 k/arm already sits on the loss plateau. The fvlmoe loss row is the sharpest statement of the whole lesson: the force branch demonstrably helps fit the demonstrations (0.0020 vs 0.0028 — it can read where in the press the label is) and that fit buys zero closed-loop behaviour — the loss is not the metric, in its purest form yet. What would move the number, in order: fix the instruction pathway (the lesson-16 follow-up), close the force loop faster than the chunk (shorter n_exec, or a wrench history), or a task where force decides the majority of episodes — which is T2, and lesson 18's opening.

The routing stats — the plumbing works even though the signal is unused (result.routing; every act() decision filed under contact |F| > 0.5 N vs free space): in free space the fvlmoe router spreads tokens 20 / 40 / 30 / 10% over its four experts; in contact it concentrates 89% of all tokens onto expert 1 — the router genuinely learned a contact-vs-free split (prefix_moe's router, by contrast, parks ~87–90% on one expert in both regimes). The force token itself goes to experts 2/1 in contact (57/36%); zero the wrench and the same decisions re-route it to expert 3 (64%) while outcomes do not move — the router reads the force; nothing downstream needs it. And fraction_dropped is 0.0000 in every row: at act time a batch of one (85 tokens) has no viable group-of-16 split, the reference grouping degenerates to groups of 1 and the capacity floor of 4 never binds — the 62–67% train-time drops and the 0% act-time drops are the same mechanism seen from its two sides.

In the trace panel, an fvlmoe episode is indistinguishable from lesson 16's: approach, the position-mode descent, the Fz staircase to the click — and the mode strip stays all grey, because this model feels force and still cannot command one. The video's force strip shows no orange command line for the same reason. That grey strip survived a lesson that was entirely about force — which is precisely lesson 18's argument.

Exercises. (1) Sparse vs dense routing: train single with moe = soft (every expert, probability-weighted — ForceVLA2's flavour) on t1, then evaluate it with Compare checkpoint set to this suite's checkpoint: the "B:" rows roll on the same seeds, and result.routing shows what dense mixing does to the contact tilt (soft cannot drop tokens by construction). (2) Apply the loss the reference never applied: retrain the fvlmoe single with balance_loss on and watch two numbers — the checkpoint's train_fraction_dropped (here 0.62) should fall as the balance term spreads the router, and the eval's contact tilt says whether the learned contact/free split survives being balanced. (3) The deliberately wrong one: "corrupt" the wrench with force_noise = shuffle at evaluation and expect a FACT-style drop. Measured (eval 261101-eval-shuffle, 100 episodes/arm, same seeds): fvlmoe 47/100 vs 45/100 at off; none 51/100, outcome-for-outcome identical to its off row; the other arms ±2–3 episodes. The lesson is two traps deep. First, shuffle permutes the batch dimension, act() evaluates one observation at a time, and a permutation of one row is the identity — the wrench reaches the model untouched, so nothing about force reliance was tested. Second, the ±3 is not corruption either: on CUDA, torch.randperm(1) still consumes one draw from the per-episode generator (on CPU it does not — both measured), so the flow-noise stream shifts and a few borderline episodes land differently — which is why the none arm, the only one that never calls apply_force_noise, is the only bit-identical one. A "corruption" that leaves the input untouched measures only RNG displacement; zero and gaussian are the act-time tests, and shuffle only bites where batches are real (training-time ablations). Read the knob's help text — and the port's docstring — before trusting a knob.

Round 2 — making the model listen

The round-1 analysis pre-registered the attack: fix the instruction pathway (CFG), close the force loop faster than the chunk (n_exec), and only then re-grade the board. The protocol was fixed before any round-2 run: R1 re-rolls the round-1 checkpoint under n_exec overrides alone (no retrain — isolates the force-timing lever); R2 retrains two singles (none and fvlmoe) with instruction dropout 0.1 and sweeps the 2×2 grid cfg_w {1, 3} × n_exec {8, 2}, choosing the recipe on the none arm's button match — the force-blind arm, so the choice is never tuned on the gated arm; R3 re-runs the canonical five-arm suite with dropout 0.1 and re-grades all five claims under that one recipe. Bars fixed throughout (plan §6).

Why CFG has nothing to amplify here, measured (outputs/round2_equiv/probe_cfg_gap.py: \(\lVert v_{\mathrm{cond}} - v_{\mathrm{blank}}\rVert / \lVert v_{\mathrm{cond}}\rVert\) on 10 held-out T1 observations at varied episode phases): on the round-1 none arm the instruction moves 3.4% of the velocity field at τ = 1 (the most text-dependent point of the whole flow) — and on the dropout-retrained arm it moves 1.6%, with the conditioned and blank xy-velocities of the first 8 chunk steps at cosine ≥ 0.996. Instruction dropout, whose job was to make the conditional-vs-blank contrast explicit, instead trained the contrast away: with the interpolant leak intact the velocity target is predictable without the words, the blank samples fit the same field, and the network converges toward text invariance — after which w = 3 amplifies a 1.6% nudge to ~5%, orders short of flipping a mode. CFG is an amplifier, not a generator: it can only magnify a difference the training objective paid for, and this objective never paid for one. The cure for c6 is upstream of sampling — in the loss (weight the leak-free high-τ region, or an explicit mode head) or in a non-BC signal (lesson 19's RL) — not in the sampler.

The gate stays red, and the board says why in its own rows. The four healthy arms all moved up together, 51–56 → 54–57, with nothing escaping the clump: button match is again chance (54–58%), the aborts are gone (0 in all four, the R1 reactivity effect), and the twin and noise rows score above the raw-wrench row (58 vs 56). The new green row is real but was not engineered: re-trained with dropout and rolled under the recipe, prefix_moe hovers above the buttons and times out in 88 of 100 episodes (11 dig in, 1 succeeds), the paper's 0% row reproduced to within a point. Unresolved here, and said plainly: round 3 changed two things at once for that arm (the dropout retrain AND w = 3 at act time), and the diagnostic that would separate them, one eval of the same arm at w = 1, n_exec 8, was not run because the shared GPU was taken by other users' jobs when the suite finished. Its routing gives a hint: the prefix MoE parks 65–66% of tokens on one expert in both contact and free space (fvlmoe concentrates 94% onto its expert 1 in contact vs 55% free, so its learned contact split survived the retrain). A router that cannot tell contact from free space gets placed in front of the trunk, drops 54.4% of its tokens at training batch size (round 1: 66.9%), and the trunk then reads a mangled scene. That is exactly the fragility Table 3's 0% row names, and this run shows how little it takes to tip it over. Two rounds, one verdict on the levers: reactivity fixes press hygiene (aborts → 0) and costs nothing; guidance on the instruction cannot fix a contrast its training objective erased; the gate needs the instruction pathway fixed in the loss first, then a task where force decides most episodes, which is lesson 18's T2.

Tech development — what broke, how it was found, what changed

Every change that was needed to make this lesson's experiments and claims work, in the order it was found: symptom, how it was found, cause, change, take-away. Master copy: docs/force_vla_school_techdev.md.

17.1 — parity needed a dtype pin. The reference rounds router logits and expert inputs to bfloat16 (a TPU artefact); the port is fp32. Change: the fixture generator pins those two dtypes to fp32 to compare the math → max |port − reference| = 9.5e-07.

17.2 — the capacity cap works at training and vanishes at inference. Instrumentation showed 62–67 % of tokens dropped by the capacity cap during training, 0 % at act time. Cause: the reference's own grouping rule — at batch 1 the 85 tokens factor into groups of 1, where the capacity floor of 4 can never bind. (A "17-token group" is likewise impossible: 17 is prime.) Ported as-is, documented; the routing stats report both regimes.

17.3 — the reference's inference path cannot run. sample_actions concatenates a None prefix into the LIMoE call while the cached prefix is unused. The port uses one definition for loss and act.

17.4 — round 1: force did nothing. Every arm landed at 43–56/100; fvlmoe 45/100 = exactly the force-blind bar; zeroing the force changed nothing (twin +1). Diagnosis, measured: the language ceiling from 16.3 caps every arm near the 50 % button lottery; one 10 Hz wrench sample per 0.8 s open-loop chunk arrives too late to gate a press; behaviour cloning gives no incentive to use force at all. Notably fvlmoe's flow loss was 29 % lower and bought zero behaviour. Take-away: loss is not the metric; hiding the quantity from the camera is necessary, not sufficient. Round 2 (below) attacks the first two causes.

17.5 — "shuffle the force" was a no-op. At batch 1 a random permutation is the identity — and on CUDA randperm(1) still consumes a generator draw (on CPU it does not), so the measured ±2 pt jitter was RNG-stream displacement, not corrupted force. The lesson states the two-layer mechanism.

17.6 — a restart stamped a healthy run "failed". The lab's startup sweep marks every non-terminal run dir failed; an agent's out-of-app training was running at the time (the jobs check printed it, but the shell chain did not gate on it). The training was unaffected and its own done() repaired the status. Change: restarts only behind a probe that exits non-zero on any active job.

17.7 — round 2's grid stalled on its own job. The 8-cell evaluation grid stopped after two cells: "refusing: 1 compute process on the GPU". The driver's idle check counted the agent's own 5-arm suite, launched in parallel to save wall time. Change: overlapping one's own jobs became an explicit opt-in (ALLOW_SHARED=1). Take-away: an idle check cannot tell your jobs from someone else's — overlap must be explicit, never the default.

17.8 — new knobs could not run through the live lab. The running server imports task modules at startup, so its forms rejected the new parameters (HTTP 422), and restarts are gated. Change: a driver writes a standard job directory and runs the same job entry point in a fresh container, so the runs still appear in the app's lists; after the next gated restart the forms carry the knobs.

17.9 — faster re-planning fixed the presses, not the score. Re-planning every 2 steps instead of 8 took force failures from 45 to 7 to 0 out of 700 episodes, yet fvlmoe moved only 45 → 47 → 48 and the twin gap stayed at −1. Cause: the aborts were real chunk staleness, but stopping a press only needs fresher camera frames, not the wrench — and the binding constraint was always the button choice (match 45–56 %, chance). Take-away: separate failure modes before crediting a lever; removing failures that never bound the score leaves the score flat.

17.10 — classifier-free guidance had nothing to amplify. Across guidance weight {1, 3} × re-plan {8, 2}, button match stayed at 45–48.5 %. Found by measuring the gap guidance works on: ‖v_cond − v_blank‖ / ‖v_cond‖ was 3.4 % before instruction dropout and *1.6 %* after it (cosine ≥ 0.996). Cause: the flow interpolant already reveals which button the demo pressed, so the target is predictable without the words, and training with blanked instructions converges toward ignoring them even harder. Take-away: guidance amplifies a difference the training objective paid for; it cannot create one — measure the conditional-minus-blank gap before tuning w.

17.11 — the training curve overstated success. The periodic 20-seed closed-loop points ended at 70 % and 65 %; the 100-episode held-out evals measured 46 % and 44 %. A 20-seed estimate carries a ±20-point interval and used a different seed window. The board reads only the 100-episode evals.

17.12 — an unexplained collapse, honestly left open. In round 3 the MoE-before-the-trunk arm fell to 1/100 (88 timeouts, 11 aborts) — confirming the paper's "MoE before the VLM collapses" row — after scoring 52 in round 1. Two things changed at once for that arm (the dropout retrain and guidance weight 3), and the one evaluation that would separate them was blocked by a busy GPU. Take-away: when a pre-registered recipe changes two things, budget the separating diagnostic up front.

17.13 — a mechanism quantity was never stored. Round 1's instruction-following rate could not be recomputed afterwards: results stored success per instruction and press counts, never the target per episode. Change: evals now store button_match. Take-away: store the quantity a claim's mechanism depends on, not just the headline rate.

Knobs

  • Preset: single trains one model with the chosen force route on Task's demos (with the eval-points series); claims_suite trains the five Table-3 arms (none / prefix_linear / prefix_moe / concat_after / fvlmoe, all on t1) sequentially into ONE checkpoint whose evaluation fills the whole M2 board.
  • Force route (single preset): the six doors, prompt_bins included — the suite always trains its five fixed rows.
  • MoE router: top1_capacity is the reference; top1 removes only the capacity cap; soft is a dense mix (every expert, probability-weighted) — ForceVLA2's flavour, here for contrast.
  • Experts: 2 / 4 / 8 (the reference uses 4). Capacity per group-of-16 is round(16/E) with a floor of 4, so 8 experts means every buffer is floor-sized.
  • Add the balance loss: ADDs the Switch load-balancing aux (coef 0.01) that the reference computes and never applies — exercise 2's knob.
  • Steps / Learning rate / Batch / Demos / Seed: the fit() schedule, as in lesson 16; suite arms use seed + 101·i.
  • Instruction dropout p (round 2): per training sample, replace the instruction with the blank <unk> text with probability p — the conditioning dropout CFG needs. 0.0 trains exactly the round-1 model; the round-2/3 runs used 0.1.
  • Episodes / Eval seed / video (evaluate): held-out episodes per group, shared across groups so gaps are paired; the claims want 100.
  • CFG weight on the instruction (evaluate, round 2): each Euler step combines vblank + w·(vcond − vblank); 1.0 is the plain conditioned model (the blank branch is skipped entirely). Useful only on a checkpoint trained with instruction dropout — the same knob is on lesson 16's evaluate form.
  • Executed steps override (evaluate, round 2): 0 = the checkpoint's trained n_exec, else execute 1–16 steps of each chunk before re-planning (clamped to the chunk length) — the reactivity lever, also on lesson 16's form.
  • Wrench at act time (evaluate): off / zero / shuffle / gaussian, applied to every evaluated arm with no retrain; while off, an fvlmoe arm is additionally rolled at zero and gaussian — the twin and FACT claim rows.
  • Compare checkpoint (evaluate, optional): a second nano-force-vla checkpoint rolled on the same seeds; its arms render as "B: ..." rows (never in claims) — the cross-checkpoint hook exercise 1 uses.

The suite checkpoint holds all five arms labelled (kind "nfv-suite", the lesson-16 pattern), so one evaluate sees every arm, adds the twin and noise rows from the fvlmoe arm without retraining, and files every act() decision's routing under contact or free space. The claims board stays the referee: the bars came from ForceVLA's Table 3 and the plan's M2 gate before the runs, and the measured column says what a 9 M-parameter model on a 96×96 testbed actually did with a sense of touch.
