The question

A transformer policy such as the one in task 10 (ta-vla) repeatedly has to answer "which of these tokens is relevant to this one?". Attention is the mechanism that does it, and in its simplest form it is a soft dictionary lookup: the question (query) is compared with a label on every stored item (key), and what comes back is a blend of the items' contents (values), weighted by how well the labels matched. This task isolates exactly that, with no robot in the way: a handful of key–value pairs, one key to look up, one attention layer.

The task

Each example has n_pairs pair tokens and one query token. Keys are drawn without repetition from 16 key ids, values are random from 16 value ids. A pair token is the sum of the key's embedding and the value's embedding, so one vector carries both. The query token is the embedding of one of those keys plus a learned "?" vector where the value would be. The model must output the value that went with that key. There are no position embeddings, so position cannot help: the only way to the answer is matching keys. The loss is the cross-entropy on the value; guessing gives \(1/16 = 6.25\%\) accuracy and a loss of \(\ln 16 \approx 2.77\).

The method

Every token \(x_i\) (width \(d_\text{model} = \text{heads} \cdot d_k\)) is multiplied by three learned matrices, so that each token plays three roles at once:

$$q = x_\text{query} W_Q,\qquad k_i = x_i W_K,\qquad v_i = x_i W_V$$

Q: "what am I looking for?", K: "what do I contain?", V: "what do I hand over if I am picked?". Only the query token asks, so there is one \(q\) per head and one \(k_i, v_i\) per token.

The score of token \(i\) is how well its key matches the question, scaled so that long vectors do not saturate the softmax; the softmax turns scores into weights that sum to 1; the output is the weighted sum of the values:

$$s_i = \frac{q \cdot k_i}{\sqrt{d_k}},\qquad \alpha = \operatorname{softmax}(s),\qquad o = \sum_i \alpha_i\, v_i$$

Each head does this with its own matrices; the heads' outputs are concatenated and mixed by an output projection, and a linear readout turns the result into 16 value scores. The attention code is the shared mini-transformer in lab/tasks/minitf.py — the same module the next attention tasks use.

Theory — attention is a differentiable dictionary

A hash map does this task's lookup in one line — but a hard "take the item whose key equals the query" is not differentiable, so nothing upstream of it could be trained. Attention replaces the argmax with a softmax-weighted blend of all items, and that one change makes the whole pipeline trainable: the gradient of the loss flows through the weights \(\alpha\) into every key and query, telling them how to move so that the right item wins the blend. The mechanism predates transformers — Bahdanau et al. (2014) introduced it so a translation model could reach back into a variable-length source sentence; Vaswani et al. (2017) kept only this part and discarded the recurrent network around it. In matrix form, per head:

$$\operatorname{Attn}(Q,K,V)=\operatorname{softmax}\!\left(\frac{QK^\top}{\sqrt{d_k}}\right)V$$

Why three separate projections instead of scoring the raw vectors? A raw dot product \(x_q \cdot x_i\) is symmetric: it forces one vector to be both the question and the label, and here it would be worse still — a pair token literally carries key + value in one sum, so \(W_K\) must project out the key part (or the value would pollute the match), \(W_V\) the value part, and \(W_Q\) phrases the question in the same learned \(d_k\)-dimensional subspace. Separate maps make the three roles independent. Why \(\sqrt{d_k}\): for zero-mean, unit-variance, independent components,

$$\operatorname{Var}(q\cdot k)=\textstyle\sum_{j=1}^{d_k}\operatorname{Var}(q_j k_j)=d_k,$$

so unscaled scores grow with the key size and push the softmax into saturation, where the gradient to every losing token vanishes. The divisor is a softmax temperature: a larger one flattens the weights towards a uniform average, a smaller one sharpens them towards a hard lookup. The model still tunes its own effective temperature by scaling what \(W_Q\) and \(W_K\) produce — watch the weights sharpen as the loss falls off its plateau.

The architecture

n = n_pairs, T = n + 1 tokens (the query attends to the pairs and to itself), d_model = heads · d_k. The dashed line is V travelling to the weighted sum; the loss sits on the readout only, so everything before it — the embeddings, \(W_Q, W_K, W_V, W_O\) — is shaped by whether the right value comes out.

Attention: scores, softmax, weighted sum
def forward(self, x_q, x_kv=None, mask=None):
    x_kv = x_q if x_kv is None else x_kv  # self-attention unless told otherwise
    q, k, v = self.split(self.q(x_q)), self.split(self.k(x_kv)), self.split(self.v(x_kv))
    scores = q @ k.transpose(-2, -1) / self.dh**0.5  # [B, H, Tq, Tk]: how well q matches k
    if mask is not None:
        scores = scores.masked_fill(~mask, float("-inf"))
    attn = scores.softmax(-1)  # each query's weights over the keys sum to 1
    mixed = (attn @ v).transpose(1, 2).reshape(x_q.shape)  # weighted sum of values
    return self.out(mixed), attn
Lookup model: the query attends over the stored pairs
def forward(self, keys, vals, qpos):
    x = self.tokens(keys, vals, qpos)
    out, attn = self.mha(x[:, -1:], x)  # attn: [B, H, 1, n+1]
    return self.readout(out[:, 0]), x, attn

What to watch

While the run trains, the live attention panel under the charts shows one heatmap per head for a fixed probe example (the same tokens at every snapshot, about 60 snapshots per run), plus the Q, K, V vectors of that probe when the vector grids are on. Hover a heatmap cell to see which token it is. Early on the weights are spread out; the interesting moment is when the weight on the token whose key equals the query's concentrates.

Measured in this app (default settings: 2 heads, d_k = 16, 4 pairs, 1500 steps, lr 3e-3, GPU; seeds 0, 1, 2):

  • The loss sits at chance (2.78 at step 5, 2.75 at step 25, train-batch accuracy 9–10%) and then falls off a cliff: 31% accuracy at step 50, 100% at step 100 (loss 0.05; 0.001 by step 150). The three seeds first reached 99% at steps 100, 110 and 100. The plateau is the model not yet having a way to compare the query with the pair tokens; it ends when \(W_Q\) and \(W_K\) line up.
  • With one head, 99% came at step 185 (seed 0); with four heads at step 70. One head is enough for this task, extra heads only make it quicker.
  • At the end of the default run the probe's query attends 0.68 (head 0) and 0.72 (head 1) to the token carrying its key, against 0.08 and 0.05 to itself — far from one-hot, yet 100% correct, because the readout also absorbs the blur. With 8 pairs the same probe gave 0.55 and 0.81.
  • The model trained on 4 pairs scores 100% (2000 examples each) on 2, 3, 5, 6, 7, 8 and 12 pairs: without position embeddings the lookup does not depend on how many items are stored.

After training, evaluate a checkpoint and drag the stage slider of the inference stepper through embed → Q/K/V → scores → softmax → mixture → readout for one probe example; the table of bars under "scores" and "softmax" lists the token behind each number.

Knobs

  • Heads: parallel lookups with their own \(W_Q, W_K, W_V\); d_model = heads · d_k. Several heads are redundant here and mainly speed up the first hit (see above).
  • d_k: width of each head's key space. Larger values give the keys more room; the scores are divided by \(\sqrt{d_k}\) so the softmax stays usable.
  • Key-value pairs per example: more pairs means more competitors for the softmax. The evaluation's pairs in the probe can be set differently from training (2–12).
  • Training steps, learning rate, seed: batch 256 is fixed, fresh examples every step (so the accuracy curve is also held-out accuracy). Runs take about 2–3 s on the GPU.
