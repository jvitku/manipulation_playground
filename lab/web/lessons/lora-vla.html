The question

Lessons 15–19 trained every policy from scratch: nanoVLAs of a few million parameters that fit on any GPU and learn a task in minutes. Real VLAs do not start from scratch. They are pretrained — hundreds of millions to billions of parameters that already read images and words — and the work is to adapt one to a new robot and a new task. The standard way to adapt is fine-tuning, and fine-tuning a 450 M-parameter model means training 450 M numbers, storing a gradient for each and two AdamW moments for each. On this course's 10 GB RTX 3080 that does not fit: training every parameter of SmolVLA ran out of memory at batch 16 after 8.96 GiB allocated (measured below, arm D). So how do you adapt a large VLA on a small budget? This lesson writes LoRA from scratch — a frozen pretrained network plus low-rank adapters, about 1 % of the weights — and asks four questions of it: does it reach the standard fine-tune's success, what does it actually save in memory and on disk, can it be folded back into the weights for free, and is what full fine-tuning changes really low-rank, as LoRA assumes?

The task

The model. SmolVLA (lerobot/smolvla_base, 450 046 176 parameters as loaded, 452 974 816 with the adapters): a SmolVLM2 vision-language model cut to 16 text layers reads the cameras, the instruction and one state token; a 16-layer action expert of width 720 denoises the action chunk by flow matching, attending to the VLM's keys and values — lesson 16's recipe at roughly 60× the parameters. It was pretrained on a different arm (SO-100), with different cameras, state and actions: the gantry is a new embodiment for it.

Adapting it to the gantry. The two course cameras (static and wrist, 96×96) become its camera1/camera2; its own preprocessing upsamples them to 512×512 for SigLIP, and after the connector's pixel shuffle each camera is 64 tokens. The instruction plus a newline is tokenised to 48 tokens. The 8-D state and the 4-D action (dp xyz + gripper) are z-scored with the demo set's own statistics (the base's belong to the SO-100) and zero-padded to SmolVLA's 32 dims; the loss masks the padded action dims away. Chunk 16, execute 8 — the course standard (smolvla_base was trained at 50/50; the expert's chunk tokens carry no learned positional table, so the weights load unchanged and simply see shorter chunks). The new-embodiment projections — state_proj [32→960], action_in_proj [32→720], action_out_proj [720→32] and the time-action MLP, 1 635 152 parameters — are trained by every arm.

Data and budget. The first 200 of lesson 15's canonical demos, 5 000 steps per arm at batch 16 (80 000 samples, ~11.6 passes over T3's 6 911 demo steps), AdamW with SmolVLA's preset (betas 0.9/0.95, weight decay 1e−10, grad-norm clip 10), 500 warm-up steps and a cosine to 2.5 % of the peak. The peak learning rates were fixed per mode before any run and not tuned: head 1e−3, LoRA 2e−4, expert_full 1e−4 (SmolVLA's own). Each suite (three arms in sequence + the D probe) took 81 minutes on the GPU.

T3 first, T0 by pre-registration. The task was the user's choice: T3 peg insertion, whose hole sits up to ±4 mm off the visible marker and which lesson 19's nano base solved 2 % of the time. Because a comparison between arms means nothing if every arm is at the floor, a fallback was written into outputs/lora_vla/PREREG.txt before the T3 evaluation: if every arm is ≤ 5 % on T3, the identical suite runs on T0 reach & grasp (pick up a visible cube, lift it 5 cm within 10 s), and the two success claims are judged there; the task-independent claims stay on the T3 suite. It fired: A 0/100, B 0/100, C 3/100 on T3. 95–100 % of the T3 episodes ended in a force abort (mean peak |F| 25.3–26.0 N). The cause is the action space, not the adaptation: 62 % of the T3 demo steps are hybrid force control (search and insert run on a force target with dpz exactly 0), and this lesson's action is dp xyz + gripper, so the contact phase has no channel to be imitated in — the same channel gap as lessons 15, 18 and 19 (tech development 20.5).

The method: a low-rank update to frozen weights

(a) What fine-tuning changes. Every linear layer of a pretrained network holds a weight matrix \(W\in\mathbb R^{d\times k}\) (out × in). Fine-tuning on the new task, whatever the optimizer, ends at

$$W' = W + \Delta W,\qquad \Delta W\in\mathbb R^{d\times k}.$$

Full fine-tuning treats all \(d\,k\) entries of \(\Delta W\) as free. LoRA's whole idea is a bet on the structure of \(\Delta W\): not on what the network knows (that is \(W\), kept), but on how little has to change to point that knowledge at a new task.

(b) The low-rank hypothesis. Aghajanyan et al. measured the intrinsic dimension of fine-tuning: optimise only a random low-dimensional subspace of the parameters, projected back into the full space, and ask how small it can be. With only 200 trainable numbers they tuned RoBERTa to 90 % of full fine-tuning's performance on MRPC — and the larger the pretrained model, the smaller the subspace it needs. If the useful directions of change are that few, each layer's update should be well approximated by a matrix of low rank \(r\):

$$\Delta W \approx B\,A,\qquad B\in\mathbb R^{d\times r},\quad A\in\mathbb R^{r\times k},\quad r\ll\min(d,k).$$

A rank-\(r\) matrix is a sum of \(r\) outer products: \(A\) picks \(r\) directions in the input space ("down", \(k\to r\)), \(B\) says how each of them should move the output ("up", \(r\to d\)). Everything outside those \(r\) input directions passes through the layer exactly as pretrained.

(c) The forward pass. \(W\) is frozen; only \(A\) and \(B\) train, and \(\Delta W\) is never formed while training:

$$h = W x + \frac{\alpha}{r}\,B\,(A\,x).$$

The bypass costs \(r(d+k)\) multiply-adds per token instead of \(d\,k\). The factor \(\alpha/r\) makes the learning rate rank-independent: with Adam every entry of \(B\) moves by roughly the learning rate per step whatever \(r\) is, so the size of \(BA\,x\) — a sum over \(r\) terms — grows with \(r\); dividing by \(r\) keeps the effective step of \(\Delta W\) about constant, and \(\alpha\) is set once (here \(\alpha = 2r = 32\), scale 2). Sweeping the rank knob then changes the adapter's capacity, not its learning rate (Hu et al.: the scaling helps "to reduce the need to retune hyperparameters when we vary r").

The forward pass: the frozen layer plus the scaled bypass B(A x)
def forward(self, x: Tensor) -> Tensor:
    y = self.base(x)  # [..., out]   W x + b, frozen
    h = self.dropout(x).to(self.lora_A.dtype)  # [..., in]
    d = F.linear(F.linear(h, self.lora_A), self.lora_B)  # [..., r] -> [..., out]
    return y + (self.scale * d).to(y.dtype)  # B = 0 at init: exactly y

(d) Initialisation: step 0 is the pretrained model. \(A\) gets nn.Linear's own kaiming-uniform init, \(B = 0\). Then \(BA = 0\), and the adapted network computes exactly the pretrained output — bit for bit, a unit test. The gradients at step 0 show why the two halves are initialised differently. With \(g = \partial L/\partial h\):

$$\frac{\partial L}{\partial B} = \frac{\alpha}{r}\,g\,(A x)^{\top} \neq 0,\qquad \frac{\partial L}{\partial A} = \frac{\alpha}{r}\,B^{\top} g\,x^{\top} = 0\ \text{ while } B = 0.$$

\(B\) moves first (through the random directions \(A\) offers); \(A\) starts learning once \(B\) is non-zero. Both at zero would leave both gradients zero forever. This is the third time the course uses the move: lesson 13's residual actor and lesson 19's residual on a frozen nanoVLA start with a last layer near zero, so training starts at the base policy, not near it. There the residual was added to the action; here it is added to the weights — \(W + \Delta W\) with \(\Delta W\) starting at 0.

(f) Where the memory goes — and what LoRA does and does not save. A parameter that trains costs 16 bytes here: its fp32 master copy (4), its gradient (4) and AdamW's two moments (8). A frozen one costs its storage, 2 bytes in bf16. So D's parameter state alone is 450 M × 16 B = 7.2 GB (6.7 GiB) before a single activation is stored — on a card with 9.65 GiB usable it could not work, and it did not: CUDA OOM after 8.96 GiB, in fp32-master precision and in lerobot's as-loaded bf16 alike. C's 99.9 M trainable parameters cost 1.6 GB of state, B's 4.6 M cost 73 MB. That is the saving LoRA is famous for — and at this scale it is not where most of the memory goes. Measured peaks at batch 16 (torch max_memory_allocated, GiB): A 3.21, B 3.61, C 4.74.

  • Activations dominate. state_proj feeds the VLM's prefix, so every arm back-propagates through all 16 frozen VLM layers and stores their activations (2 × 64 image tokens, 48 text tokens and the state token per sample, 16 samples). The head-only arm A trains 0.36 % of the weights and already peaks at 3.21 GiB = 0.68 × C — a floor no adapter method can go below at this batch.
  • What LoRA removes is C's fp32 expert copy, its gradients and its AdamW moments: about 1.3 GiB of the measured 1.53 GiB between A and C.
  • What LoRA adds is 0.40 GiB over A: 128 adapter paths whose (fp32-upcast) inputs are stored for the backward pass.

So B/C = 3.61/4.74 = 0.76, and the pre-registered "≤ 60 %" claim is red. LoRA's headline saving (GPT-3: 1.2 TB → 350 GB of training VRAM) is an optimizer-state-dominated number at 175 B parameters; at 450 M and batch 16 the levers for activation memory are the batch size and gradient checkpointing. The disk saving is the one that scales without caveats: B's adapter file (the trainable tensors only) is 18.35 MB, against 399.58 MB for C and ~918 MB for a full checkpoint — one base model plus one small file per robot or task.

(g) Merging: zero inference latency. After training, the bypass can be folded into the weight:

$$W' = W + \frac{\alpha}{r}\,B A,$$

an ordinary \(d\times k\) matrix in an ordinary nn.Linear. The merged network has exactly the base architecture and speed; the adapter disappears. In exact arithmetic the merge is exact. Measured on a real batch (predicted flow velocity, fp32, TF32 off): max |vadapter − vmerged| = 1.37e−6 on the T3 suite and 3.10e−6 on T0, against a mean |v| of 0.29–0.31 — rounding. Merged into the bf16 weights the model is stored in, it is not exact: 2.34e−2 and 5.47e−2, i.e. several percent of the output. Why: bf16 keeps 8 significant bits, so neighbouring representable values are ~0.8 % apart and every entry of \(W'\) is rounded to the nearest one; an entry of \(\Delta W\) smaller than half that spacing relative to its \(W\) entry vanishes in the sum. The fix is to keep A and B in fp32 (the code does, whatever the base dtype) and merge into an fp32 copy, or to serve unmerged.

merge: W + ΔW added in fp32, then cast to W's dtype (where bf16 rounds)
def delta_weight(self) -> Tensor:
    """ΔW = (alpha / r) · B @ A  [out, in], in the adapter dtype; rank <= r."""
    return self.scale * (self.lora_B @ self.lora_A)  # [out, r] @ [r, in] -> [out, in]

@torch.no_grad()
def merge(self) -> nn.Linear:
    """A plain nn.Linear computing W + ΔW (the base's dtype/device): zero extra latency."""
    b = self.base  # W = b.weight [out, in], b.bias [out]
    m = nn.Linear(b.in_features, b.out_features, bias=b.bias is not None,
                  device=b.weight.device, dtype=b.weight.dtype)  # fmt: skip
    w = b.weight.to(self.lora_A.dtype) + self.delta_weight()  # [out, in], add in fp32
    m.weight.copy_(w.to(b.weight.dtype))  # [out, in] in W's dtype: a bf16 W rounds here
    if b.bias is not None:
        m.bias.copy_(b.bias)  # [out], unchanged
    m.requires_grad_(False)
    return m

(h) Which layers. Adapters sit on the attention projections q, k, v and o of all 16 VLM text layers and all 16 action-expert layers — 128 layers. Attention is where Hu et al. put LoRA: they adapted only the attention weights and froze the MLPs, and found that spreading a fixed budget over more attention matrices at low rank beats a single matrix type at high rank. Adapting the VLM's attention also lets B change something C never touches (lerobot's recipe freezes the whole VLM). Left out: the MLPs (gate/up/down: 75 % of a VLM layer's weights, 71 % of an expert self-attention layer's), and the vision tower (SigLIP + connector, 98 M), whose general image features are kept as pretrained — and whose activations over the full-resolution patch grid no frozen arm has to store.

(i) Mixed precision at this scale. The nano models of lessons 15–19 stayed plain fp32; at ~5 M parameters there was nothing to save. smolvla_base stores the VLM and 96.6 M of the action expert in bf16, and trained as loaded, AdamW would keep bf16 weights and bf16 moments. An update smaller than half a bf16 spacing of its weight (~0.4 % of its magnitude) then rounds to nothing. Measured on C at one peak-learning-rate step (the expert elements that the fp32 step moved, re-applied to bf16 storage): 72 % of them would have been lost in the 100-step pilot, 83 % on the T3 suite, 85 % on T0 (tech development 20.2). So every trainable tensor gets an fp32 master copy, frozen weights stay bf16 (they are never updated), and the forward/backward runs under torch.autocast(bfloat16) on the Ampere card — bf16 compute, not bf16 weights; unlike fp16 it needs no loss scaling. The same rounding explains (g): a merge into bf16 is one large update to bf16 weights.

Motivation — why each choice is in this experiment

Why SmolVLA. It is the open VLA built to be fine-tuned on a single consumer GPU (450 M parameters, a flow-matching action expert like lesson 16's), with a maintained reference fine-tuning recipe in lerobot. A 7 B OpenVLA would not even load for training on this card; a nanoVLA has nothing pretrained to adapt.

Why three trained arms. LoRA only means something between two baselines: what you get by adapting less, and what standard practice gets by adapting more. All three train the same new-embodiment projections from the same data, steps and batch; only what else trains differs.

Why head-only is the floor. It is the linear-probe question: is the pretrained network already right, with only the interface to the new robot missing? If A matched C there would be nothing for LoRA to do. On T0 it reaches 13 % where B reaches 99 % — the internals have to change.

Why expert_full is the reference. It is lerobot's own fine-tuning recipe for SmolVLA (VLM frozen, whole action expert trained) — what a practitioner would actually run, and the strongest arm that fits the card.

Why measure D. "Full fine-tuning does not fit" is the premise of the whole lesson; the probe makes it a measurement (3 steps, every parameter, peak memory or the OOM) instead of an assumption.

Why the spectrum. LoRA assumes the update is low-rank. C's update is not constrained at all, so its singular values are the one place in the experiment where the assumption can be checked rather than imposed.

Theory — LoRA, intrinsic dimension, and what comes next

LoRA (Hu et al. 2021, arXiv 2106.09685) "freezes the pre-trained model weights and injects trainable rank decomposition matrices into each layer of the Transformer architecture"; on GPT-3 175 B it cut the trainable parameters 10 000× and the training memory 3×, with quality on par with full fine-tuning and "no additional inference latency" (the merge). Section 7 looks at the learned \(\Delta W\) itself and finds it of very low intrinsic rank — the check this lesson repeats on C.

Intrinsic dimension (Aghajanyan, Zettlemoyer & Gupta 2020, arXiv 2012.13255): fine-tuning succeeds inside a random subspace of a few hundred to a few thousand dimensions; 200 parameters reach 90 % of full RoBERTa fine-tuning on MRPC, and pretraining lowers the intrinsic dimension. LoRA turns this observation into a per-layer parameterisation that is learned rather than random.

QLoRA (Dettmers et al. 2023, arXiv 2305.14314) is the next step: it "backpropagates gradients through a frozen, 4-bit quantized pretrained language model into Low Rank Adapters", fine-tuning a 65 B model on one 48 GB GPU. Quantising the frozen base attacks the part of the memory LoRA leaves alone — the resident weights (0.9 GB here). Not implemented in this lesson: every number on this page is a bf16 base with fp32 adapters.

SmolVLA (Shukor et al. 2025, arXiv 2506.01844): a compact VLA that "can be trained on a single GPU and deployed on consumer-grade GPUs or even CPUs"; its own fine-tuning freezes the VLM and trains the action expert — arm C.

OpenVLA (Kim et al. 2024, arXiv 2406.09246), the 7 B open VLA, states in its abstract that it "can be fine-tuned on consumer GPUs via modern low-rank adaptation methods" — LoRA is the standard way large VLAs are adapted to a new robot, which is why it gets a lesson.

How to read it. The memory claim is red, and it should be. The bar came from the paper's 2/3 saving at GPT-3 scale; here activations through the frozen VLM dominate every arm, the head-only arm already sits at 0.68 of C, and LoRA can only remove what lies between A and C (method (f)). "Matches" on T3 is a floor artefact. Two arms at 0 % and 3 % "match within 10 points" while the same board says LoRA does not beat training the heads alone — a matching claim needs a task where the reference succeeds, which is exactly why the fallback was pre-registered (tech development 20.6). T0 is where the comparison has signal, and it is decisive both ways: adapting the internals matters (+86 points over the heads), and LoRA on 4.6 M parameters lands within one episode of the standard recipe on 99.9 M. One caveat stays: T0 is easy for C (100/100), so "matches" there is a ceiling comparison; a task between floor and ceiling would separate the arms more finely.

The spectrum: what share of ||ΔW||² the top-k singular values carry
def energy_top_k(s: Tensor, k: int) -> float:
    # ...
    e = s.double() ** 2  # [n] s_i^2: the energy along each singular direction
    tot = float(e.sum())  # ||ΔW||_F^2
    return float(e[:k].sum()) / tot if tot > 0 else 0.0

Tech development — what broke, how it was found, what changed

Every change that was needed to make this lesson's experiments and claims work, in the order it was found: symptom, how it was found, cause, change, take-away. Master copy: docs/force_vla_school_techdev.md.

20.1 — lerobot 0.6.1 cannot live in the lab's Python. The brief's recipe was a venv made from the lab interpreter. Found by: reading the installed lerobot's wheel METADATA in the fvb-vla image before writing the Dockerfile — Requires-Python: >=3.12; the lab image is python:3.11 (robosuite's numpy<2 world). Change: the /opt/vla venv brings its own CPython 3.12 (uv-managed python-build-standalone under /opt/uv-python; uv is uninstalled from the lab python afterwards), then torch 2.7.1+cu126, lerobot[smolvla]==0.6.1, mujoco 3.3.0, imageio. The lab's python is untouched (3.11, torch 2.5.1, numpy 1.26). Image 7.79 → 13.93 GB (+6.1 GB). Take-away: a dependency's Python floor is as binding as its torch pin — check both.

20.2 — smolvla_base stores the action expert in bf16 too, so lerobot's recipe updates bf16 weights. Nothing looks wrong in training. Found by: listing parameter dtypes after from_pretrained: the 350 M VLM AND 96.6 M of the expert are bf16 (the expert is built from the VLM's bf16 text config); only the re-created cross-attention k/v (1.6 M) and the projections are fp32. AdamW on bf16 weights keeps bf16 moments, and an update below half a bf16 ulp (~0.4 % of the weight) rounds away. Measured at one peak-LR step of the expert-only fine-tune: 83 % (T3) / 85 % (T0) of the moved expert elements would have been lost in bf16 storage (72 % in the 100-step pilot). Change: every trainable tensor gets an fp32 master copy, frozen weights stay bf16, compute runs under torch.autocast(bfloat16) (Ampere bf16, no loss scaling). Take-away: at 450 M, "bf16 training" must mean bf16 compute, not bf16 weights.

20.3 — an adapter is a drop-in only if it keeps the attributes the host reads. SmolVLA's attention does x.to(layer.self_attn.q_proj.weight.dtype) before every projection. Found by: reading smolvlm_with_expert.py before writing nfv.lora. Change: LoRALinear exposes weight / bias / in_features / out_features as read-through properties of the frozen base (unit-tested with a bf16 base). Take-away: wrap by interface, not just by forward().

20.4 — LoRA did not cut training memory to 60 %; activations dominate at 450 M / batch 16. B peaked at 3.61 GB vs C's 4.74 GB (ratio 0.76, claim NOT CONFIRMED on both suites). Found by: the per-arm peaks — the head-only arm A (1.6 M trainable) already peaks at 3.21 GB = 0.68 x C, a floor no adapter method can beat at this batch. Cause: (i) state_proj feeds the VLM prefix, so every mode back-propagates through all 16 frozen VLM layers and stores their activations (2 cameras x 64 image tokens at 512 px + 48 text + 1 state token); (ii) the 0.91 GB of weights are resident in every arm; (iii) what LoRA removes is C's fp32 expert gradients + AdamW moments (~1.2 GB). B's +0.4 GB over A is the 128 adapter paths (the adapter input is upcast to fp32). D (every parameter) does not fit at all: CUDA OOM after 8.96 GB at batch 16, in fp32-master and in as-loaded bf16. Take-away: LoRA saves memory in proportion to the frozen parameters' optimizer state; the paper's 2/3 saving is a GPT-3-scale, optimizer-dominated number. For activation memory, the levers are batch size and gradient checkpointing.

20.5 — on T3 every arm force-aborts: the dp-only action space cannot express the expert's contact phase. T3: A 0 %, B 0 %, C 3 % on 100 shared seeds; 95-100 % of the episodes end in a force abort (mean peak |F| 25-26 N), against the nano base's 31 % aborts / 67 % timeouts. Found by: the outcome counts + splitting the T3 demos by controller mode: 62 % of the demo steps are hybrid force control in search/insert (f_target_z −3.8 N, dp_z exactly 0), while the free-space descent runs at −14.7 mm/step in position mode. Cause: the lesson's action is dp xyz + gripper (as specified), so the force-controlled phase has no channel; one descent step past contact commands 14.7 mm x 800 N/m ≈ 12 N, two reach the 25 N abort, and a chunk executes 8 steps open-loop. Change: none to the arms (pre-registered); the pre-registered fallback (every arm <= 5 % on T3) ran the identical suite on T0. Take-away: the action space decides what can be imitated — the same channel gap as 15.7, 18.8 and 19.18.

20.6 — at the floor, "matches within 10 points" is confirmed by vacuity. On T3 the claim B ≥ C − 0.10 read CONFIRMED (0 % vs 3 %, gap CI −8.5..+2.7) while B ≥ A + 0.10 failed — two arms at 0 % "match". Found by: reading the T3 board before the T0 run. Take-away: a matching claim needs a task where the reference succeeds; the floor fallback was pre-registered for exactly this, and on T0 (A 13 %, B 99 %, C 100 %) both success claims are decisive.

20.7 — what full fine-tuning changed IS low-rank (a result, kept here as a calibration). C's ΔW = W_after − W_before on three expert attention layers: the top-16 singular values carry 0.88 / 0.83 / 0.98 of ||ΔW||²_F on T0 (0.88 / 0.85 / 0.98 on T3); a random Gaussian matrix of the same shapes puts 0.07 / 0.17 / 0.07 there (five draws: 0.172–0.174 for the 320 × 320). The late o_proj update is essentially rank 5 (singular values 1.21, 1.05, 0.88, 0.74, 0.68, then 0.30). The merge is exact in fp32 (max |Δv| 3.1e-6 on a real batch) but not in bf16 storage (5.5e-2): keep adapters fp32 and merge in fp32 before casting.

Knobs

  • Preset: single = one arm; claims_suite = A head, B LoRA, C expert_full in one job, plus the D "train everything" memory probe, which runs first on a clean GPU.
  • Mode (single preset): head (the new-embodiment projections only), lora (head + LoRA on every attention q/k/v/o of the VLM and the action expert) or expert_full (lerobot's recipe: VLM frozen, whole action expert).
  • LoRA rank r: 4, 8, 16 (default) or 32; parameters per layer = r × (in + out) (exercise 1).
  • LoRA alpha: \(\Delta W = (\alpha/r)\,BA\); default 32, \(\alpha = 2r\) is the common choice.
  • Task: t3 (default, peg insertion; the user's choice for this lesson), t0 (reach & grasp, the pre-registered fallback), or t1 / t2.
  • Training steps per arm: 5000 is the pre-registered budget (26–28 minutes per arm on the RTX 3080).
  • Batch size: 16 (exercise 2).
  • Peak learning rate: 0 = the mode's pre-registered default (head 1e−3, lora 2e−4, expert_full 1e−4); warm-up min(1000, steps/10), then a cosine to 2.5 %.
  • Demos (first n episodes): 200 of lesson 15's canonical demos.
  • Seed: initialisation and batch sampling; the suite's arms use seed + 101·i.
  • Measure D (train everything) first: the suite always measures it; a single run only when ticked.
  • Shared held-out seeds (evaluate): every arm rolls on the same seeds, 100 by default.
  • Eval seed (evaluate): shifts the window inside the task's eval-seed block.
  • Render the same-seed video (evaluate): every arm on one seed, one after the other.
  • Eval workers in parallel (evaluate): up to 3, one SmolVLA (~1 GB of VRAM) per worker; the simulator is CPU-bound.
