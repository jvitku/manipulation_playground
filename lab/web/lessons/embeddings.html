The question

A robot policy usually has to be told what to do. The command reaches the network as a vector, and there are many ways to make that vector. This task trains the same flow-matching policy four times on the same demonstrations and the same closed-loop test scenes, changing only how the command is encoded, so the four success curves are directly comparable. The commands are the four of the contact scene: insert into the red hole, insert into the blue hole, press gently (2 N) and press firmly (6 N). There is no camera: the network sees the peg position, the perceived positions of the two holes (on by default — see the knobs below), the last 10 force readings, and the command.

The four encodings

  • One-hot (4 numbers): a 1 in the slot of the command, 0 elsewhere. No notion of similarity: all commands are equally far apart.
  • Binary (2 numbers): the two bits of the command id (0–3), bit 0 = id mod 2 and bit 1 = id div 2. The same information as one-hot in half the width, but a different geometry: insert blue and press firmly share a bit (bit 0), while insert red and press firmly differ in both. The code groups commands by an arbitrary numbering, unlike one-hot, where all four commands are equally far apart.
  • Text (d_embed numbers): the command's words as token ids, looked up in an nn.Embedding table and averaged. The table is trained together with the policy: the network must discover, from the loss alone, that “gently” and “firmly” mean different forces. This is a miniature of how a VLA conditions on language: TAVLAMini in src/fvb/ta_tutorial/nets.py has the same self.lang = nn.Embedding(vocab, d) and feeds the looked-up word vectors into the transformer prefix; here the pooled vector is just concatenated to the MLP input.
  • Continuous (3 numbers): the command written in robot terms — [perceived x of the target hole (0 for a press), target force in N (0 for an insert), is-insert flag]. It is the only code that carries meaning rather than identity.
The four encodings of a command
def enc_raw(kind: str, task: np.ndarray, est: np.ndarray) -> np.ndarray:
    # ...
    if kind == "onehot":
        return np.eye(4, dtype=np.float32)[task]
    if kind == "binary":
        return np.stack([task & 1, (task >> 1) & 1], 1).astype(np.float32)
    if kind == "text":
        return np.array([c2d.tokens(int(t)) for t in task], np.int64)
    ins = task <= 1
    x = np.where(ins, est[np.arange(len(task)), np.minimum(task, 1)], 0.0)
    f = np.array([c2d.PRESS_N.get(int(t), 0.0) for t in task])
    return np.stack([x, f, ins.astype(float)], 1).astype(np.float32)
The conditioned denoiser: encode the command, concatenate, denoise
class CondDenoiser(nn.Module):
    # ...
    def __init__(self, arch: dict):
        # ...
        self.kind, self.key = arch["enc"], ENC_KEY[arch["enc"]]
        self.d = enc_dim(self.kind, arch["d_embed"])
        self.emb = None
        if self.kind == "text":
            self.emb = nn.Embedding(len(c2d.VOCAB), arch["d_embed"], padding_idx=0)
    # ...
    def encode(self, e: torch.Tensor) -> torch.Tensor:
        if self.emb is None:
            return e.float()
        m = (e != 0).float().unsqueeze(-1)  # mean over the real tokens, not the padding
        return (self.emb(e) * m).sum(1) / m.sum(1).clamp_min(1.0)
    # ...
    def forward(self, x_t, t, cond):
        obs = torch.cat([cond["state"], cond["torque"], self.encode(cond[self.key])], 1)
        return self.net(x_t, t, {"obs": obs})

Theory — what a conditioning code decides

The command vector \(c\) enters the network once, concatenated with the state and force history, so the only thing the four arms change is the geometry the first layer sees — and that geometry decides what is easy to learn. A one-hot gives each command its own orthogonal axis: the first layer holds one independent weight column per command, nothing is shared, and the width grows with every command added. The 2-bit code carries the same information in half the width, but its geometry is an accident of the numbering: commands that share a bit share a direction whether or not they share anything else, and the network must carve XOR-like regions to undo it. Information content is not the issue — representation is.

The learned embedding decouples width from command count. Each word is a trainable vector and the command is the masked mean of its words, $$c = \frac{\sum_i m_i\, E_{w_i}}{\sum_i m_i},$$ with \(E\) the table and \(m\) zero on the padding. The rows of \(E\) receive gradient from the same flow loss as the policy, so commands that demand similar behaviour are free to end up nearby — and shared words (“insert”, “press”) are literally shared parameters, so data for one command shapes the code of another. That is the property that scales: with many commands, swap the trained-from-scratch table for a pretrained language encoder and a new phrasing arrives already placed in a meaningful space (BC-Z conditions on frozen sentence embeddings for exactly this; the VLA lessons' language path is the same idea). The continuous code is the opposite limit: a human has already resolved the command into physical quantities, so the network only has to follow numbers — at the price of needing that resolver, and its perception of the holes, at run time.

  • Jay Alammar, “The Illustrated Word2vec” — the same idea drawn out, the gentlest way in.
  • Perez et al., “FiLM: Visual Reasoning with a General Conditioning Layer” (2017) — the main alternative to concatenation: conditioning as a learned per-feature scale and shift.
  • Jang et al., “BC-Z: Zero-Shot Task Generalization with Robotic Imitation Learning” (2022) — conditioning a robot policy on frozen language embeddings, and what that buys for unseen commands.

The architecture

Exactly one encoding block feeds the network in an arm. All arms use the same loss as the earlier tasks, $$L = \left\lVert v_\theta(x_t, t, s, c) - (e - x_0) \right\rVert^2,\qquad x_t = t\,e + (1-t)\,x_0,$$ with \(s\) the state and force history and \(c\) the encoded command.

The data and the knobs

The expert is the contact scene's scripted expert on two holes (red and blue); only successful demonstrations are used. Each hole's position reaches the network as a perceived value: the true x plus a 1 cm error drawn once per episode (the stand-in for a perception module). The Tell every arm where the holes are option controls whether these two numbers are in the state of every arm. Turn it off and you get a confounded comparison: the continuous code still contains the target hole's x, while one-hot, binary and text can only guess which hole is meant, so they could not do better than choose a hole by feel. Leave it on to compare the encodings on what they are for: telling which command. Even with it on, cont differs from the other arms in kind: it hands the network a pre-resolved target coordinate, while one-hot, binary and text must learn the mapping “command → which of the two observed hole positions”; that difference is exactly what the comparison measures. Each arm trains Training steps per encoding steps, so a full run costs about four single trainings; use Encodings to train to run one arm. The arms train one after another, but the charts plot each against its own step count, so the curves overlay at equal training effort.

Normalisation is part of the representation

State and force are z-scored with the training set's statistics, as everywhere. One-hot and binary vectors are passed through unnormalised: they are categories, and z-scoring {0, 1} would silently make the value of a bit depend on how common the command is. Token ids have no scale at all, and the embedding table is learned. The continuous code is z-scored, because it mixes metres (|x| < 0.13), newtons (0–6) and a flag: without it the 6 N entry would dominate the 0.1 m one by a factor of sixty. The scale of a representation is a design decision, not a detail.

What to expect — measure, don't assume

There are no prior numbers for this comparison in the repository, so none are quoted here; the charts are the result. These are the hypotheses the run lets you test, with the reasoning behind each:

  • One-hot and binary carry identical information; any gap between their curves is geometry plus optimisation noise. Binary packs four commands into two axes, so the network must carve more complicated regions out of a smaller space. Do not trust a single run: a few points of difference between two arms is usually seed noise at this size (the viewer's table gives a Wilson 95% interval).
  • Text must learn its mapping. It starts from random word vectors and has to organise them from the loss; it may lag early and catch up, or stay behind if the budget is small. What it can offer in return is shared structure (“insert” appears in two commands, “press” in two) — whether the network exploits that at four commands is exactly what the per-command charts show.
  • Continuous can interpolate — a force of 4 N is a meaningful input between gentle and firm, while a one-hot vector for a fifth command is meaningless — but this run only ever uses the four values, so the interpolation benefit is not tested here; what is tested is whether a physically meaningful, normalised code trains faster.

Read the success overlay for the answer, the per-command charts for where an encoding fails (a press at the wrong force ends as a timeout or a force abort; the wrong hole is a distinct outcome), and the loss as a health check only, as in the earlier tasks.
